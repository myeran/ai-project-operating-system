# Registry Adapter Contract Document

**System:** AI Project Operating System  
**Status:** Proposed for Approval  
**Scope:** Contract only; no database or storage technology is selected here.  
**Canonical State Reference:** `system-contracts-and-state-model.md`

## 1. Purpose

The Registry Adapter provides the single controlled interface to the Project Registry.
The Registry is the canonical index of Project Instances and is used for project
resolution, duplicate detection, metadata retrieval, and controlled metadata updates.

The Adapter does not own Project State, Project Knowledge, project artifacts, or
lifecycle decisions. It does not replace the Project Resolver, Orchestrator, or State
Adapter.

## 2. Entity Model

Each Registry entry represents one independent Project Instance:

```yaml
project_registry_entry:
  project_id: <stable unique id>
  project_name: <canonical display name>
  owner: <human owner or pending confirmation>
  status: proposed | active | blocked | awaiting_approval | completed | cancelled
  current_phase: <canonical lifecycle phase>
  os_version_reference: <bound OS version>
  workspace_location: <canonical workspace reference>
  created_date: <creation timestamp>
  last_activity: <last accepted activity timestamp>
  version: <monotonic metadata version>
  audit_metadata:
    last_updated_by: <authorized actor>
    last_updated_at: <timestamp>
    history_ref: <audit history reference>
```

### Entity Invariants

- `project_id` is stable and unique.
- `project_name` is required for display and resolution; it is not the sole identity.
- `status` and `current_phase` must use canonical values.
- `version` increases on every accepted metadata update.
- `created_date` is immutable.
- `last_activity` changes only when an accepted project activity occurs.
- Registry metadata must not become a second Project State model.
- A Registry entry must reference one Project Instance only.

## 3. Operations

All operations receive a request context containing `request_id`, `correlation_id`,
`actor`, and timestamp. Mutating operations also require authorization context and,
where applicable, an expected version.

### 3.1 Create

**Input**

```yaml
create_project_registry_request:
  project_id: <optional proposed id; generated if absent>
  project_name: <required name>
  owner: <required or explicitly pending>
  status: proposed
  current_phase: Discovery
  os_version_reference: <required bound version>
  workspace_location: <required canonical reference>
  request_context: <required>
```

**Output**

```yaml
create_project_registry_result:
  outcome: created | duplicate | rejected
  project_registry_entry: <entry when created>
  audit_record_id: <when accepted or rejected>
```

**Validation**

- Required identity, owner state, OS reference, and workspace reference exist.
- The proposed ID is unique, or a stable ID is generated by the owning bootstrap boundary.
- The project name is normalized for comparison without changing the display name.
- No exact or materially similar active Project Instance is silently duplicated.
- Initial phase and status are canonical.
- Creation is attributable to an authorized Bootstrap Workflow request.

**Failure Cases**

- Existing exact match → return `duplicate`; do not overwrite.
- Similar or ambiguous match → return `ambiguous_match`; require resolver/user decision.
- Invalid fields → `rejected`; no partial entry.
- Registry unavailable → `unavailable`; no project creation is reported as complete.

### 3.2 Find

**Input**

```yaml
find_project_request:
  project_id: <optional>
  project_name: <optional>
  owner: <optional narrowing field>
  include_archived: <explicit boolean>
  request_context: <required>
```

At least one supported lookup field is required. `project_id` has priority over name.

**Output**

```yaml
find_project_result:
  outcome: found | not_found | duplicate | ambiguous | unavailable
  matches:
    - project_id: <id>
      project_name: <name>
      status: <status>
      current_phase: <phase>
      last_activity: <timestamp>
      location: <reference>
```

**Duplicate Handling**

- Exact `project_id` must resolve to at most one entry.
- Exact normalized name with multiple entries returns `duplicate`, never an arbitrary match.
- Similar names return `ambiguous` with match reasons and require a user or Orchestrator decision.
- Archived entries are excluded unless explicitly requested.

### 3.3 Get

**Input**

```yaml
get_project_request:
  project_id: <required stable id>
  request_context: <required>
```

**Output**

```yaml
get_project_result:
  outcome: found | not_found | unavailable
  project_registry_entry: <complete entry when found>
  read_version: <entry version>
```

`Get` is read-only and returns the Registry entry only; it does not load the full
Project State.

### 3.4 Update

**Input**

```yaml
update_project_registry_request:
  project_id: <required>
  expected_version: <required for compare-and-commit>
  changes: <allowlisted metadata changes>
  source_task_id: <required>
  request_context: <required>
```

**Allowed Fields**

- `owner`, when ownership is explicitly authorized.
- `status`, when the Orchestrator or authorized human decision permits it.
- `current_phase`, only as a projection of an approved lifecycle transition.
- `os_version_reference`, only through the controlled OS update process.
- `workspace_location`, only through an authorized relocation process.
- `last_activity`, only as system-maintained activity metadata.

`project_id`, `created_date`, and audit history are not directly editable. `project_name`
changes require an explicit rename operation or approval and must re-run duplicate checks.

**Validation**

- Project exists and is uniquely identified.
- Actor is authorized for every changed field.
- Current version equals `expected_version`.
- New values are canonical and consistent with Project State.
- A phase or status change has an Orchestrator transition context.
- Affected project metadata is not silently changed during another operation.

**Audit Requirements**

Every accepted or rejected update records:

- Request and correlation IDs.
- Project ID.
- Actor and source task/decision.
- Before and proposed values for changed fields.
- Previous and new version when committed.
- Timestamp, outcome, and reason.

## 4. Access Rules

| Action | Authority |
|---|---|
| Read Registry | Runtime Gateway, Project Resolver, Bootstrap, Orchestrator, and authorized read-only reviewers through the Adapter |
| Propose metadata change | Orchestrator; Bootstrap for creation; authorized Skills/Workers only through a typed proposal |
| Approve strategic/ownership change | Human Owner or System Owner according to existing governance |
| Commit Registry change | Registry Adapter after validation and authorization; never a direct client write |
| Modify Project State | State Adapter contract, not Registry Adapter |
| Modify OS rules or global Registry schema | System Owner through architecture governance |

The Registry Adapter is the technical commit boundary, not the business decision
authority. The Orchestrator remains responsible for lifecycle and project-action
decisions.

## 5. Validation Rules

### Identity and Uniqueness

- Stable IDs are unique and never reused.
- Names are compared using a deterministic normalization rule while preserving the original display name.
- Duplicate checks occur before creation and before approved renames.
- A similar match must be surfaced; similarity is not proof of identity.

### State Alignment

- Registry `status` and `current_phase` must agree with the canonical Project State snapshot used for the operation.
- Registry metadata is a resolution index, not an alternative state authority.
- If Registry and Project State disagree, the operation fails closed and is escalated for reconciliation.

### Concurrency and Version

- Mutations use compare-and-commit with `expected_version`.
- A version conflict never overwrites the newer entry.
- Retry requires a fresh read and a new Orchestrator decision.

### Audit and Atomicity

- No successful result is returned before the Registry mutation and its audit record are accepted together.
- Partial creation is not reported as a completed Project Instance.
- Unknown fields, malformed values, and missing authorization are rejected.

## 6. Error Handling

| Error | Required Behavior |
|---|---|
| `project_not_found` | Return a structured not-found result; Resolver decides whether a new-project flow is valid. |
| `duplicate_project` | Stop creation; return exact matches and require Continue/New/Compare/Merge choice. |
| `ambiguous_project` | Stop automatic routing; show matches and request clarification. |
| `invalid_state` | Fail closed; do not update Registry to hide the inconsistency; escalate reconciliation. |
| `version_conflict` | Reject commit; reload, re-evaluate, and retry only through authorized flow. |
| `registry_unavailable` | Stop creation, resolution-dependent execution, and state claims; report inability to verify the source of truth. |
| `unauthorized_operation` | Reject and audit; do not downgrade silently. |
| `invalid_request` | Reject before mutation and return required corrections. |

Errors returned to the user are rendered by the Response Renderer through the
appropriate clarification, escalation, or fail-closed response contract.

## 7. Runtime Integration

```text
Runtime Gateway
        ↓ validated request
Project Resolver
        ↓ Find / Get
Registry Adapter
        ↓ unique resolution
Bootstrap Workflow or Lifecycle Orchestrator
        ↓ create/propose metadata change
Registry Adapter
        ↓ committed registry result
State Adapter
        ↓ canonical Project State load/commit
Response Renderer
```

### Runtime Gateway

Classifies the request and passes it onward. It does not read or write Registry directly.

### Project Resolver

Owns match interpretation: exact, no match, duplicate, or ambiguous. It uses the
Adapter as the only Registry access path.

### Bootstrap Workflow

After a confirmed no-match result, proposes creation with initial `Discovery` and
canonical initial status. It does not report completion until Registry, Project State,
workspace reference, and audit requirements are satisfied.

### State Adapter

Owns the canonical Project State. Registry and State commits must be coordinated by
the owning runtime workflow so a Registry entry cannot claim an initialized project
whose State was not initialized successfully.

### Orchestrator

Consumes resolved metadata and State snapshots, controls lifecycle, and proposes
authorized Registry projections such as phase/status updates.

## 8. Testing Criteria

The contract is ready for implementation only when the following behavior can be
tested without selecting a storage technology in this document:

1. **Create:** a valid no-match request creates one entry with canonical initial metadata.
2. **Exact Find:** an existing ID resolves to exactly one entry.
3. **Name Find:** exact and similar matches are distinguishable.
4. **Duplicate Protection:** repeated creation does not create a second entry.
5. **Get:** a complete entry is returned without Project State leakage.
6. **Update:** an authorized allowlisted update increments version and records audit metadata.
7. **Unauthorized Update:** forbidden fields or actors are rejected and audited.
8. **Version Conflict:** stale updates fail without overwriting newer data.
9. **Invalid State:** Registry/State disagreement fails closed.
10. **Unavailable Registry:** resolution-dependent actions stop and return an escalation/error result.
11. **Bootstrap Boundary:** Project creation is not reported complete until Registry and State initialization are consistent.
12. **Runtime Routing:** Gateway → Resolver → Adapter is the only Registry access path.

## Approval Criteria

Approve this contract only when:

- Registry has one clear owner and source-of-truth role.
- Registry is not used as a second Project State model.
- Create, Find, Get, and Update behavior is unambiguous.
- Duplicate, conflict, malformed, and unavailable cases fail closed.
- Read, proposal, approval, and commit authorities are separated.
- The contract can support the Minimal Runtime Slice without selecting implementation technology.

**Implementation authority required next:** explicit approval of this contract followed
by a separate bounded implementation plan for the Adapter; no code or storage selection
is authorized by this document.
